# DigitalMate production metrics view

Assets are adapted from DigitalMate `dashboard/e2e-performance` (commit `c07077d`). The view reads `data/production-model-history.json`, separately from nightly E2E data. `.github/workflows/collect-production-model-metrics.yml` publishes a 35-calendar-day aggregate daily to the imported `digitalmate` branch and triggers Pages deployment. Configure the `PRODUCTION_GATEWAY_KEY` Actions secret in the dashboard repository. The runner must be able to reach the gateway. Collection uses up to three concurrent daily windows and logs each completed window. A failed collection leaves the previous aggregate intact.

Only daily model aggregates are published; raw logs and request IDs are never written. The gateway rows are calls, not user questions. All traffic on the configured gateway is included; production versus test traffic is not independently classified. Unknown-status records make the selected model/day failure rate unavailable. Missing values stay unavailable, not zero.

Metric definitions (`metrics_version: 4`):

- **Complete-day anchor.** Every summary card uses `complete_through`, the newest Asia/Shanghai day whose collection window closed; a model without data for that day is unavailable. `partial_day` (today) is marked in charts and tables but never feeds a summary card. Same-clock comparisons use the actual `window_end` collection cutoff, not the later publication time.
- **Volume-weighted means.** The collector stores `duration_sum_ms` and `duration_sample_count` per model/day; `query_ms` remains only as a legacy display value. The dashboard computes means as `sum / count` across the selected scope and never averages per-day means with equal weight. TTFT and TPOT keep `*_sum_ms` + `*_sample_count` for the same reason.
- **Request-level percentiles.** `duration_p50_ms` and `duration_p95_ms` are nearest-rank percentiles over the raw successful durations of the day and require 20 samples. When a merged row spans several models, the dashboard shows the min–max interval and leaves it unavailable if any contributing source with samples lacks the percentile. No daily-mean median is labelled as a request percentile.
- **Strict streaming.** TTFT and TPOT use only successful calls with `stream === true`. Conflicting or missing stream flags are unknown; explicit non-streaming calls are excluded. Successful calls with unknown streaming status are reported separately as TTFT and TPOT estimates with coverage ratios, never mixed into the main means. TTFT ≥ 95% of total duration invalidates both TTFT and TPOT; TPOT < 0.1 ms/token is also filtered out.
- **Successful-call tokens.** Displayed tokens count successful calls only and carry `token_coverage = token_sample_count / success_count`. Failed-attempt totals remain in the aggregate but are not displayed or included in successful-call means.
- **Low-volume models.** Models with fewer than 50 calls in the trailing 7 days are folded into a separate section of the comparison card and excluded from the headline status counts, so one call cannot present a 100% failure rate as fleet state.

TTFT is completionStartTime minus startTime; TPOT is (endTime minus completionStartTime) divided by (completion_tokens minus one). A previous snapshot with an older `metrics_version` is rebuilt in full once so every retained day uses the same definitions. The page rejects older snapshots until that rebuild succeeds. Other boards do not show this tab.
